# DSH Lite —— 精简 VS Code 插件技术方案

> 版本：v1（草案）　日期：2026-09-07　状态：待评审
> 定位：**全新独立插件**，与现有 `dsh-vscode`（0.5.1）并存，不动现有插件一行代码。
> 一句话：不 iframe 整站，自己做一套"只为侧边栏服务"的精简 UI，直接和 DSH 的 RPC 通道对话。

---

## 0. 结论先行

| 问题 | 结论 |
|---|---|
| 长期该不该自研？ | **该**。自研 = 可控、可维护、能随 DSH 开源版本演进；iframe 方案永远被"网页端长什么样"绑架 |
| 难度会不会很高？ | **比 0.5.x 低**。因为不需要本地认证代理（见 3.2），协议层是现成的 |
| 会不会影响现在能用的插件？ | **不会**。新扩展 ID、新目录、本地加载，两者并存互不干扰 |
| 风险点？ | DSH 0.1.x 仍是 rc 版本，协议可能变；对策见第 9 节 |

## 1. 为什么要自研（依据）

### 1.1 现状问题
现有 `dsh-vscode` 把 **整个 DSH 网页应用 iframe 进侧边栏**：设置页、模型选择、工作区/会话管理、引导卡片全部塞进窄侧栏。用户在 VS Code 里真正需要的只有——**对话流 + 输入框 + 停止/中断 + 审批 + 变更概览 + 会话切换**。

### 1.2 业界同类怎么做（本机已装，源码已核对）
| 扩展 | 面板实现 | 配置项 | 配置项性质 |
|---|---|---|---|
| Claude Code 2.1.218 | **自研 UI**（webview/index.js 4.8MB） | 14 | 全宿主行为：终端/原生 UI、权限模式、自动保存、快捷键 |
| Codex 26.901 | **自研 React + Tailwind** | 8 | 全宿主行为：CodeLens、回车行为、review 投放、语言 |
| dsh-vscode 0.5.1 | **iframe 整站** | 12 | 也是宿主行为（host/port/自启/桥接） |

**共同点：三家都不在插件里放模型、API Key、账号、会话配置** —— 这些属于 CLI/服务端。我们的目标同样是"插件只做交互，配置归 DSH"。

### 1.3 官方没有"嵌入精简模式"
已在 DSH 0.1.2-rc.1 客户端包中核查（`dsh-client-ui-chat` / `ui-conversation` / `ui-workspace` / `client-connection`）：
`embed` / `compact` / `iframe` / `panelMode` **全部 0 命中** → 没有官方精简视图可依赖，减法必须自己做（这也是选自研而非"等官方"的理由）。

## 3. 已核实的源码事实（架构地基）

> 路径基准：`~/.local/node-v24/lib/node_modules/@deepseek-ai/dsh/node_modules/@deepseek-ai/`

### 3.1 RPC 通道
- DSH 的全部 RPC 走 **WebSocket `/api/remote.mux`**（`dsh-api-gateway/lib/index.js:11`）。
- session 命名空间已暴露 17 个方法：`prompt` / `fork` / `attachment` / `updateQueue` / `cancel` / `page` / `follow` / `rename` / `create` 等；方法表以 **typert descriptor** 形式固化在各包 `typert.remote-client.js`，浏览器端另有冻结副本 `dsh-api-remotes/lib/client.js`（0.1.2 起是浏览器方法表唯一来源，已踩过坑）。
- **契约来源（权威）**：`dsh-api-session-controller/lib/typert.remote-client.js` 里的 zod schema 与 descriptor —— 升级 DSH 后第一件事就是 diff 这个文件。

### 3.2 鉴权（已实测修正 ⚠ 原方案此处有误）

> 2026-09-07 用真实实例抓帧时复核源码，**推翻了初稿的一条推断**，以本节为准。

**真实判定链**（`dsh-client-connection/lib/index.js` 的 `requestRejection()`）：

```js
requestRejection(request) {
  if (!isTrustedApiRequest(request, this.trustedHosts)) return 403;  // ① Host/Origin 围栏
  return this.browserAuth.isAuthenticated(request) ? void 0 : 401;   // ② cookie 校验
}
```

- **① 围栏**：Host 必须 loopback 或 trusted-host；`Sec-Fetch-Site: cross-site` 直接拒；带 `Origin` 时必须与 Host 同源。→ 违者 **403**
- **② cookie**：`/api/*`（含 WS 升级）**都要有效签名 cookie**。→ 无 cookie **401**
- `authorizeIndex()` 只作用于**静态资源 fallback**（`GET /`），与 `/api/*` 无关

**实测**：`GET /` → 401 文案；WS 升级无 cookie → 401；unary 无 cookie → 401；带 cross-site 头 → 403。

**修正后的结论（结论方向不变，理由要换）**：
- cookie **必须要有**，来源是「启动令牌换 cookie」：`dsh --profile web` 的 stdout 打出 `?token=` 地址 → `GET` 该地址（`redirect:'manual'`）→ 303 的 `Set-Cookie`。
- 令牌是**进程内存态**，只有插件**自己拉起 dsh** 才拿得到 → 沿用 0.5.1 策略：**自起自有实例**，端口被 `dsh-auth`/`foreign` 占用时回退空闲端口，不复用外部实例。
- 但从 **Node 侧**发起请求可以任意设置 `Cookie` 头，且 Node 的 `fetch`/`ws` 不自动带 `Origin` → **天然过围栏，依然不需要 0.5.x 那套本地认证代理**（代理是 webview 跨站 iframe 的专有问题）。
- ✅ 已端到端验证：起进程 → 换 cookie → Node 直连 WS → 拿到 29 个会话 / 738 条事件。

详见 `docs/api/remote-mux.md`。

### 3.3 事件流（消息从哪来）
- `session.follow`：先给 `snapshot`（头部 + cursor + records + hasMore + projections），后续 `entry` 增量帧；`session.page` 拉历史页。
- 客户端实现参考：`dsh-api-session-controller/lib/client.js` 的 `SessionEventStream`（`RemoteJournalStream` 子类，`follows: right === left + 1` 保证无空洞）。
- 记录形态：`{ type: "event"|"chunks", event }`，事件带 `seq / time / data`，surface 事件带 `surfaceOp`（`append` 或 `{op:"replace",start,end}`）与 `sourceEventSeqs`。

### 3.4 会话列表
- `createSessionControlStream(... remote.session.control(signal))`：`baseline` + 后续帧 → 会话清单与状态（标题/运行态/投影值）从这里来，不需要网页端 UI。

### 3.5 需要展示/处理的内容（来自事件类型）
`user/message`、`assistant/message`（含 chunk）、`tool/result`、`turn/start`、`command/run|done`、`compaction/*`、`approval`（审批包 `dsh-client-ui-approval`）、附件（图片走 `session.attachment` / 历史图片缓存）。

## 4. 架构设计

```
┌──────────────── VS Code 扩展宿主（Node）────────────────┐
│  ProcessManager   探测/启动/停止 dsh web，解析 stdout 的就绪地址   │
│  RpcClient        WebSocket /api/remote.mux（typert 帧编解码）   │
│  SessionStore     control 流（会话清单）+ follow/page（消息）    │
│  Command          send / stop / newSession / openInBrowser …    │
│  Bridge(宿主↔UI)  postMessage 协议（版本化）                    │
└───────────────────────────┬──────────────────────────────┘
                            │ postMessage（自定协议 v1）
┌──────────────── Webview（React + TS）───────────────────┐
│  会话选择条 │ 消息流（Markdown/工具/审批/diff）│ 输入框 + 附件   │
└────────────────────────────────────────────────────────┘
                            │ WebSocket / HTTP（Node 侧发起）
┌──────────────── DSH 服务（本机 dsh web）─────────────────┐
│  /api/remote.mux（RPC） │ session.control / follow / page      │
└────────────────────────────────────────────────────────┘
```

**核心原则**
1. **UI 只渲染，不做业务**：所有状态由宿主维护，webview 只收状态快照与增量。
2. **协议版本化**：宿主↔UI 的 postMessage 带 `protocolVersion`，不匹配时提示升级。
3. **一切以 typert descriptor 为契约**：不猜接口，升级时先 diff descriptor。
4. **降级优于报错**：任一能力拿不到就隐藏对应 UI，绝不阻塞主流程（发消息/看消息）。

## 5. 模块划分

| 模块 | 职责 | 验收点 |
|---|---|---|
| `process/` | 探测（`dsh`/`dsh-auth`/`foreign`/`down`）、自启实例、解析 `dsh web:` 就绪地址、退出清理 | 能起、能停、无孤儿进程 |
| `rpc/` | WS 连接、typert 帧编解码、请求-响应关联、超时/重试/断线重连 | 断网重连后不丢状态 |
| `session/` | control 流会话清单；follow/page 消息流；send/stop/rename/新建 | 多会话切换不串消息 |
| `render/`（webview） | Markdown、代码块、工具调用折叠、审批卡片、diff 入口（调 VS Code 原生 diff） | 长消息不掉帧 |
| `config/` | `dshLite.*` 少量配置（见下） | 默认零配置可用 |
| `commands/` | 新建会话、在浏览器打开、附加选中文件、停止、清空 | — |

**配置只保留必要项**（对标 Codex 8 项）：`executablePath`、`autoStart`、`openOnStartup`、`followUpQueueMode`、`composerEnterBehavior`、`workspaceRootIndex`、`advanced.*`（调试类折叠）。
**明确不做**：模型选择、provider/API 配置、设置页、技能管理、终端 —— 需要时"在浏览器中打开"（一键跳转）。

## 6. 技术栈

| 项 | 选择 | 理由 |
|---|---|---|
| 语言 | TypeScript | 与 DSH 生态一致 |
| 宿主打包 | esbuild | 快；现有插件用 `scripts/build.mjs`，经验可复用 |
| Webview | React + Vite（或同为 esbuild） | Codex 同款；组件化便于维护 |
| 样式 | CSS 变量对齐 VS Code 主题（`--vscode-*`） | 明暗主题自适应 |
| 测试 | `node --test`（宿主）+ vitest（UI 可选） | 现有插件 198 例已用 node --test |
| Markdown | markdown-it + DOMPurify | 安全渲染 |
| 依赖 | **尽量零运行时依赖** | 减少维护面 |

## 9. 风险与对策

| 风险 | 影响 | 对策 |
|---|---|---|
| DSH 仍是 rc，协议变更 | 升级后插件失效 | 每次 DSH 升级先 diff `typert.remote-client.js` + `api-remotes`；`docs/api/` 存契约快照；宿主↔UI 协议版本化 |
| RPC/事件字段理解偏差 | 渲染错乱 | M1 阶段先做"抓帧打印"工具，用真实数据校准模型 |
| 审批/工具/附件等细节多 | 范围膨胀 | 严格按里程碑；未覆盖的能力降级隐藏，不阻塞主流程 |
| 多工作区/子会话 | 串会话 | 会话与工作区绑定，切换时全量重建状态 |
| 图片/附件 | 渲染缺失 | 走 `session.attachment`，失败降级为链接 |
| 与旧插件端口/进程冲突 | 抢占 | 新插件只用随机端口；检测到 `dsh-auth` 实例时不复用、自启自有实例（沿用 0.4.0 已验证策略） |

## 10. 开放问题（M1 抓帧后的进度）

> M1 抓帧已跑通，1、2 已闭环，3–6 需在 M3/M4 前补齐。详见 `docs/api/remote-mux.md` §5。

| # | 问题 | 状态 |
|---|---|---|
| 1 | Node 侧连 `/api/remote.mux` 是否需要 `Origin` / `Sec-Fetch-Site` 头 | ✅ 已答：**要 cookie、不要 Origin**；`Sec-Fetch-Site: cross-site` 会 403 |
| 2 | `session.control` 的字段与帧结构 | ✅ 已答：`baseline{queues,jobs,projections}`；**会话清单在 `session/list`** |
| 3 | `session.prompt` 准确参数 | ⚠ M3 前细读（`request`：`requestId`/`sessionId`/`mode: queue\|steer`/`content[]`） |
| 4 | 停止用 `session.cancel` 还是 `updateQueue` | ⚠ M3 实测 |
| 5 | 审批事件结构与回应方式 | ⚠ M4 |
| 6 | 附件/图片接口与是否需要 cookie | ⚠ M4（`session/attachment`） |

**补充坑（抓帧踩到）**：payload 必须是 `{ args: {...} }`，且 `args` 内字段名是描述符的 **wire 名**（如 `session/list` 是 `_request` 而非 `request`）。直接传参数对象会被拒：`gateway/internal`。

## 11. 开发纪律（用户明确要求）

1. **先文档后代码**：每个里程碑开工前先在 `docs/` 写清目标、接口、验收；评审通过才动代码。
2. **最小 diff**：不顺手重构、不加没要求的功能。
3. **本地验证 + 用户确认**再提交/发布（沿用现有插件已确立的红线）。
4. **中文提交信息**，完成一条勾一条并同步 README/CHANGELOG。
5. **不影响现有插件**：不修改 `dsh-vscode` 目录、不复用其扩展 ID、不改动其配置前缀。
