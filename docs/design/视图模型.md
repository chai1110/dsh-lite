> 与官方 `MutableSessionEventSource` 的关系：Lite **不维护全量事件窗口**，只维护「可读条目序列」

## 2. shadow 折叠（编辑重发替换，M2 第一优先级）

- 触发：事件带 `sourceEventSeqs: number[]`（编辑重发/压缩替换时由服务端给出被覆盖的旧事件 seq）。
- 算法（已实现）：`applyEvent` 开头先 `dropSeqs(sourceEventSeqs)` 过滤掉这些 seq 的既有条目，
  再按当前事件类型处理；新事件入列后视觉上即「旧消息被替换」。
- `surfaceOp: {op:'replace'}` 的 start/end 语义在不同版本可能是 seq 也可能是窗口下标，
  **Lite 不冒险做范围删除**，只依赖 sourceEventSeqs（见代码注释）。
- 验证：test/viewmodel.test.ts「编辑重发替换整段回合」—— user1+assistant2 被
  `user3(sourceEventSeqs:[1,2])` 折叠成只剩一条 user3。

## 3. 流式尾巴（chunk 累积 → message 定稿）

- `openAssistantTail()`：从尾部回溯，遇 user 边界停；返回打开的 assistant 条目。
- `assistant/chunk`：文本追加到尾巴（去重：`!endsWith(part)` 才拼）。
  无开放尾巴时（快照回放缺 chunk）允许按 seq 建流式占位条目。
- `assistant/message` 定稿：
  1. 尾巴存在、streaming、定稿文本 startsWith 尾巴文本 → **原地升级**（改 text、关 streaming，不重复渲染）；
  2. 否则关掉旧尾巴 streaming，按新 seq 追加定稿条目。
- 状态条目不参与尾巴匹配；`statusLineOf` 无命中且非 `session/*` → 未知事件兜底状态行。

## 4. 快照回放与幂等

- `applyRecords(records[])`：records 中 `{type:'event', event}` 逐条 `applyEvent`；
  `{type:'chunks', chunks:[…]}` 是中间窗口（97 条实测），**不消费**——快照里最终态由
  assistant/message 记录表达，重放 chunk 只会产生脏尾巴。
- 幂等：`seenSeqs` Set 去重，重复帧忽略；`reset()` 清空（切会话/重连全量替换时由调用方决定）。
- `lastSeq` 供调试与后续增量分页衔接。

## 5. 分页（未实现，挂起说明）

follow 快照实测带 `cursor` 与 `hasMore:true`（641 条 event + 97 条 chunk）。
本版 Lite 一次性消费快照内已含的 records（约 700+ 记录，实际消息几百条，可接受）。
cursor 续拉（`session/follow` 游标分页）**留待 M5 依实测契约补**：不在 M2 臆造分页参数。

## 6. UI 侧消费（provider/service）

- `SessionService.getMessages()` 把条目转 `ViewMessage[]`（id=`s<seq>`、role 映射、tool 附加 kind），
  乐观占位消息与回声去重见 service 单测。
- `SessionViewModel.onChange` → `SessionService.onChange` → provider `publish()` 全量下发，
  UI 不做增量合并（docs/design/宿主-UI协议.md §3）。
