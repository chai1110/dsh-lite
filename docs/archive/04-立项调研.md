## 2. 关键事实：端点代际断层（本立项的立足点）

本机 DSH **0.1.2-rc.1** 实测：

```
grep -rl "events.mux|events.host"  <dsh 包>   →  零命中（已删除）
grep -rl "remote.mux"               <dsh 包>   →  命中（唯一 RPC 通道）
```

- `DoggyHU/dsh4vscode` 的 README 明确写「连接 `/api/events.mux`、`/api/events.host`」。
- 这两个端点在 0.1.2-rc.1 **已不存在** → **该插件在当前版本上会失效**，且它已 17 天没更新、无 License。
- 同类地，我们自己维护的 `dsh-vscode` 在 0.1.1→0.1.2 之间也踩了同源的断裂（编辑重发失效）。

**结论**：社区里"自研精简 UI 直连 RPC"这条路**有人走过但已断在当前版本**，需要有人接上——这就是我们继续做的**硬理由**。

## 3. 三条技术路线对比（含一个被排除的选项）

| 路线 | 代表 | 优点 | 缺点 | 结论 |
|---|---|---|---|---|
| A. iframe 整站 | 现有 dsh-vscode 0.5.1、xhd2005 | 零协议工作量、功能全 | 侧栏塞网页端、要认证代理；xhd2005 文档明说 **WebviewPanel 的 iframe 端口映射带不动 DSH 客户端需要的 WS 下行** | ❌ 正是我们要摆脱的 |
| B. **自研 UI + RPC 直连** | dsh4vscode（旧版）、**我们** | 精简、可控、全保真（标题/待办/审批/附件都在） | 需跟 typert 契约，版本升级要 diff | ✅ **推荐** |
| C. 标准协议 ACP | `dsh --profile acp` | 官方标准协议、跨版本稳、有文档 | **致命限制**（见下） | ❌ 已排除 |

### 3.1 为什么排除 ACP（重要发现）

DSH 自带 `dsh-acp`：`dsh --profile acp` 起一个 JSON-RPC stdio 的 **Agent Client Protocol** 服务。看起来是"官方稳定通道"，但官方 README 的 Known Limitations 写明：

> - **No transcript replay or interactive extensions** — session deletion, fork, `session/load`, modes, commands, plans, terminals, client filesystem operations, and **elicitation** remain outside this automation surface.
> - 只支持**一个主工作区**；只支持 MCP tools。

对聊天面板来说这是致命的：

- **没有 transcript replay** → 读不到历史消息（我们 follow 流一抓就是 738 条记录，C 路线拿不到）
- **没有 elicitation** → 做不了审批卡片（M4 的核心）
- 没有 plans / modes / 终端

→ ACP 定位是"自动化/子代理/测试"，**不是给人用的交互面**。放弃。

## 4. 值不值得做（诚实两面）

### 值得的 3 条
1. **版本真空是真的**：0.1.2-rc.1 的新版 RPC 无人适配（§2），而我们已经在 M1 抓帧里把 `remote.mux` 跑通（起进程→令牌→cookie→WS→拿到 29 个会话与 738 条事件）。
2. **可控性**：第三方插件（含最活跃的 Lixxx1，alpha 0.0.4）不受我们控制；DSH 仍在 rc，协议还会变，**自有实现才能当天修**。
3. **契约沉淀可复用**：`docs/api/` 里的协议快照对我们自己、也对社区有价值（升级时 diff descriptor 即可）。

### 不值得的 2 条（也要说清）
1. **功能层面确实已有轮子**：Lixxx1 已经在做侧边栏 + 调试集成 + MCP/Skills/Hooks 管理，MIT 且活跃。若目标只是"我要一个能用的精简侧栏"，**直接用它成本更低**。
2. **维护成本真实存在**：DSH 仍是 rc，每次升级都要 diff `typert.remote-client.js` 并回归。这是持续投入，不是一次性。

### 建议的定位调整

> **从"做一个精简 DSH 插件" → 改为"做一个跟得上 DSH 版本的最小可控客户端"**。
> 不追功能（不追调试/MCP/Hooks 管理），只守住：**发消息 / 看消息 / 停止 / 审批 / 会话切换**。
> 功能要更多时，一键"在浏览器中打开"——与 Codex / Claude Code 同款取舍。

## 7. 附：本次调研顺带修正的原方案错误

写调研时复核源码，发现 `01-技术方案.md` §3.2 有一条**我此前写错了**，已在本文同批修正：

- ❌ 原写：`/api/*` 走 Host/Origin 围栏，**Node 侧直连不需要 cookie**
- ✅ 实际：`requestRejection()` = **先过 Host/Origin 围栏（403）→ 再验 cookie（401）**。WS 升级与 unary HTTP **都要 cookie**（实测：无 cookie → 401；`Sec-Fetch-Site: cross-site` → 403）
- ✅ 但**结论仍成立**：cookie 用「启动令牌换」拿到后，Node 侧自己带上即可，**依然不需要 0.5.1 那套代理**（代理是浏览器跨站 iframe 的专有问题）

详见 `docs/api/remote-mux.md`。
