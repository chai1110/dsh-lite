## 1. P1：当前代码路径可达，会造成用户可感知问题

### F. `unary()` 抛裸对象，所有错误日志退化为 `[object Object]` ⚠️ 最高优先级

**位置**：`src/rpc/unary.ts` L47、L52

```ts
if (!res.ok) {
  throw { kind: 'http', status: res.status, body: await res.text().catch(() => '') } satisfies UnaryError;
}
```

**实证输出**：
```
抛出的值 typeof = object | instanceof Error = false
String(err) = "[object Object]"
err.message = undefined
```

**影响面**（所有 catch 里用 `String(err)` 的调用点，全部丢失 status/body）：
| 文件 | 行 | 日志内容 |
|---|---|---|
| `src/connection.ts` | L164 | `[auth] 令牌换 cookie 失败: [object Object]` |
| `src/connection.ts` | L187 | `[rpc] WS 建连失败: [object Object]` |
| `src/connection.ts` | L204 | `[session] session/list 失败: [object Object]` |
| `src/session/service.ts` | 多处 | `[prompt]` / `[commands]` / `[goal]` / `[cancel]` 全同 |
| `src/panel/provider.ts` | 多处 | 所有 `ui/*` 失败同 |

**为什么这条最致命**：本仓库最典型的排障场景就是 **401 `reopen the URL printed by dsh web`**（一次性 token URL 失效）。这个信息恰好在 `body` 字段里 —— 也就是被 `[object Object]` 吃掉的那个字段。**每次排障都在盲飞。**

**修复**：`unary.ts` 改抛 `Error` 子类，保留结构化字段：
```ts
export class RpcHttpError extends Error {
  readonly kind = 'http' as const;
  constructor(readonly status: number, readonly body: string) {
    super(`RPC HTTP ${status}: ${body.slice(0, 200)}`);
    this.name = 'RpcHttpError';
  }
}
// 抛出点：throw new RpcHttpError(res.status, await res.text().catch(() => ''));
```
保持 `kind`/`status`/`body` 可读（现有 `satisfies UnaryError` 的类型约束同时满足），`String(err)` 立即可读。

### K. 端口探测最坏耗时 150s，是启动超时的 10 倍 ⚠️

**位置**：`src/process/detect.ts` L23 `timeoutMs = 3000`、L68 `PORT_FALLBACK_ATTEMPTS = 50`；调用点 `src/process/manager.ts` L143、L229

**实证**：
```
manager.ts L25: const DEFAULT_START_TIMEOUT_MS = 15000;
detect.ts  L68: export const PORT_FALLBACK_ATTEMPTS = 50;
detect.ts  L23: timeoutMs = 3000,
最坏耗时：50 × 3000ms = 150s   ← 与 15s 启动超时差 10 倍
```

且 `findFreePort(host, port, ATTEMPTS, probeService)` **未传第 5 个参数**，只能吃默认 3000ms。

**用户可感知现象**：端口被占用（比如你的主力 dsh web 已在 3082）时，扩展先串行探 50 个端口、每个等 3s 超时，UI 全程只有「正在连接…」，无进度、无取消 —— 就是历史上那次「连接卡死」的形态。

**修复**：`manager.ts` 两处调用传入与启动预算匹配的探测超时（如 `Math.min(500, timeoutMs / PORT_FALLBACK_ATTEMPTS)`），并把串行探测改为并发 `Promise.all` 或缩短 `PORT_FALLBACK_ATTEMPTS`（经验值 10 足够）。

### H. 端口回退把新端口写回 `this.opts` → 配置永久漂移 ⚠️

**位置**：`src/process/manager.ts` L237

```ts
this.opts = { ...this.opts, port: fallback };
```

**实证**：
```
初始配置端口 : 3082
一次端口回退后: 3083   ← 实例内配置被改写
```

**后果**：
1. 后续 `getSnapshot()` / 重连 / `startDsh` 全部用 3083，而 `package.json` 的 `dshLite.advanced.port` 默认仍是 3082；
2. 用户在设置里改回 3082 **无效**（实例 opts 已被覆盖，要等扩展重载）；
3. `ConnectionManager.port` 与 `ServiceManager.opts.port` 可能不一致，UI/日志出现「显示的端口 ≠ 实际监听端口」。

**修复**：用局部变量传递本轮目标端口（代码里已经有 `target` 变量了，L138），**不要把回退结果写回 `this.opts`**。`this.opts.port` 只应反映用户配置。

### I. dispose 后等待循环不退出，白等满超时 ⚠️

**位置**：`src/process/manager.ts` L223 `for (;;)`

```ts
for (;;) {
  if (spawnFailed || this.stopRequested) return this.getSnapshot();
  ...
  if (Date.now() >= deadline) { return fail('tokenParse'); }
  await new Promise((r) => setTimeout(r, pollMs));
}
```

**实证**：`disposed` 仅在 L266（`dispose()` 内）被置 `true`，循环体从头到尾**没有检查 `this.disposed`**。

**后果**：扩展卸载/停用时 `dispose()` 杀掉子进程，但已在跑的 `doStart` 仍会循环到 15s deadline 才返回 —— 停用扩展后日志还在刷、还可能在 L228 分支又 `doStart` 重启一个子进程（配合 J 缺陷，见下）。

**修复**：循环条件加 `this.disposed`：
```ts
for (;;) {
  if (this.disposed || spawnFailed || this.stopRequested) return this.getSnapshot();
```

### O. `readdirSync` 无 try/catch → 可中断整个 `activate()` ⚠️

**位置**：`src/panel/migration.ts` L214

```ts
if (!info.storageRoot || !fs.existsSync(info.storageRoot)) {   // ← 有守卫
  ...
}
...
for (const wsHash of fs.readdirSync(info.storageRoot)) {       // ← 无守卫
```

`existsSync` 通过 ≠ `readdirSync` 成功（权限不足 EACCES、目录被并发删除、SMB/网络盘抖动都会让后者抛）。异常会冒泡到 `runViewLocationMigration` 的调用点 —— 即 `extension.ts` 的 `activate()`。

**后果**：这只是一次「清理历史残留」的**非关键**迁移，却能让**整个扩展激活失败**。典型表现就是「装完了但侧栏一直空/命令没注册」。

**修复**：
```ts
let entries: string[];
try {
  entries = fs.readdirSync(info.storageRoot);
} catch (err) {
  log(`跳过视图位置清理：目录不可读 ${String(err)}`);
  await context.globalState.update(MIGRATION_KEY, true);
  return;
}
```
并在 `extension.ts` 里对 `runViewLocationMigration` 调用加 try/catch 兜底（非关键迁移不应拖垮激活）。

### M. 空白标题会话不走 fallback ⚠️

**位置**：`src/session/list.ts`

```ts
title: s.projections?.values?.title || shortId(...)
```

`"   "`、`"\n"` 都是**真值**，`||` 不会兜底。经验证：
```
"   "  →  truthy（不 fallback）
"\n"   →  truthy（不 fallback）
""     →  falsy（正确 fallback）
```
**后果**：历史下拉出现空白行，用户无法辨识/点击，也无从搜索。

**修复**：`const t = s.projections?.values?.title?.trim(); title: t || shortId(...)`。

## 2. P1-潜在：当前不可达，但改动即引爆

> 这两项我一度评为 HIGH，**实证后下调**。它们是同一类 bug（React Hooks 规则违反），但触发条件在当前代码路径下互斥，所以现在不会发作。**风险在于：它们没有测试覆盖，任何人动到相关分支就会立刻白屏。**

### T. `MsgRow` 早退绕过 `useState`

**位置**：`webview/components/messages.tsx`，函数体 L90–L207

**实证（精确行号）**：
```
L103  RET   return (        ← tool/call 分支
L121  RET   return (        ← tool/result 分支
L136  RET   return (        ← command 分支
L168  HOOK  const [open, setOpen] = useState(false);
L172  RET   return (        ← 普通文本分支
```

**为什么当前不可达**：`Messages` 用 `key={m.id}` 渲染，而 `m.id = \`s${e.seq}\``（`service.ts` L439）。`ViewModel.applyEvent` 用 `seenSeqs` 对 `evt.seq` 去重，**同一 seq 只 push 一条 entry**；且全代码库对 `.kind` **零处 push 后赋值**（已扫描确认）。⇒ 同一 React key 的 `kind` 恒定 ⇒ hook 序列恒定。

**为什么仍是隐患**：`CollapseRow` 自带 `useState`（L44），所以 L103/L121 分支实际 hook 数 = 1（来自子组件，不算 MsgRow 自身）；L168 分支 = 1。**数量碰巧一致**，纯属巧合。一旦有人调整分支结构（例如给 tool 分支加一个折叠状态、或把 `CollapseRow` 的 state 上提），立刻变成 0↔1 切换 → `Rendered more/fewer hooks than during the previous render` → 消息列表白屏。

**修复（零风险，建议一并做）**：把 `useState` 提到所有 `return` 之前：
```ts
function MsgRow({ m }: { m: ViewMessage }): ReactElement {
  const [open, setOpen] = useState(false);   // ← 提到函数第一行
  const showStreaming = Boolean(m.streaming);
  if (m.kind === 'tool' && ...) { ... }
```

### U. `App` 早退绕过 5 个 hook

**位置**：`webview/app.tsx`，`if (mismatch)` 在 L88，其后的 hook 调用：

**实证**：
```
mismatch early-return 行号: 88
return 之后的 hook 调用: 5 处 ← 这些在 mismatch 时被跳过
  L112: const slashRows = useMemo(...)
  L121: useEffect(...)
  L133: useEffect(...)
  L148: useMemo(...)
  L164: useMemo(...)
判定: ❌ 违反 Hooks 规则
```

**为什么当前不可达**：`mismatch` 只在 `case 'hello'` 且版本不符时置位（app.tsx L60-62）；而宿主 `provider.ts` **只在版本相符时才回 hello**（L148），版本不符时回的是 `host/error`（L144），走的是 `setState` 而非 `setMismatch`。两个分支互斥 ⇒ `mismatch` 永不为真。

**为什么仍是隐患**：`mismatch` 是 `App` **自身** state，一旦触发就是「同一实例 hook 数 18 → 13」的硬崩。只要将来（或旧版宿主）出现「回一个版本不符的 hello」，整面板白屏。且 `mismatch` 的兜底提示逻辑本身是有意设计的 —— 功能被这个 bug 完全废掉了。

**修复**：把 `if (mismatch)` 的提前 return 下移到所有 hook 之后，或（更好）把它做成渲染分支的最外层：
```ts
// 全部 hook 调用之后、return 之前
const mismatchBanner = mismatch ? (...) : null;
```
或在 `App` 顶部包一层 `<Gate>` 组件，`Gate` 内只放 hook-free 的 mismatch 判断，真正的 `App` 作为子组件渲染（mismatch 时不渲染 `<App>` ⇒ 组件卸载而非 hook 数变化）。

### Q. 配置读取只在 activate 时一次，无 `onDidChangeConfiguration` 监听

**位置**：`src/config.ts` L27 `getConfig()` 注释已写明「不要缓存结果」，但 `src/panel/state.ts` L35 在每次 `buildPanelState` 时读 —— 这一半是好的。问题是 `dshLite.advanced.port` / `executablePath` / `autoStart` 只在 `ConnectionManager` 构造时消费一次（`extension.ts` 装配期），**改设置不生效**，必须重载窗口。

### 6.3 对原报告判定的更正

诚实起见，以下三处原判定经实证后需修正：

1. **A（mux streams Map 泄漏）—— 原判定不成立。**
   `open()` 内注册了 `impl.onError(cleanup)`，`settleError` 会调用 errorCbs 从而触发 `cleanup` 完成 `streams.delete`。所有路径（end/error/cancel/socket close）都会清理，**不存在泄漏**。已保留我新增的 `streams.clear()` 作为显式收尾，但它属于加固而非修 bug。

2. **T / U 的危害等级 —— 已按可达性下调**（报告 §2 已写明）。两者当前都无法触发，本质是潜伏隐患；但 T 的「hook 数量碰巧一致」依赖 `CollapseRow` 自带 state 这一巧合，任何结构调整都会引爆。已按零风险方式修复。

3. **`textOf` 的 JSON 兜底 —— 保留但收窄。**
   通用兜底（`JSON.stringify`）仍存在，因为其它调用方（tool/result 等）依赖它。本次只新增「嵌套块取 text」这一层，覆盖 `chunk={type:'text',text:'…'}` 的实际形状。
